# Paper 4 — software-engineering replication: data feasibility (2026-10-28, not yet a protocol)
**Gerrit code-review votes.** The OpenStack Gerrit (review.opendev.org) REST API answers anonymous queries such as
`/changes/?q=project:openstack/nova+status:merged&o=DETAILED_LABELS&o=DETAILED_ACCOUNTS`; each change carries the Code-Review label with every reviewer's numeric vote (−2 … +2; 0 = no vote) and a persistent `_account_id` (checked on 2 nova changes: 3 reviewers, votes 0/+2/+2). Patch text (commit message + diff) is available via `/changes/{id}/revisions/current/patch`. Archived multi-project dumps also exist (Yang et al., MSR 2016 data paper: OpenStack, LibreOffice, AOSP, Qt, Eclipse — schema to be checked).
**Confound to handle before any analysis:** ±2 is reserved for core reviewers (approve / block), non-core reviewers can only vote ±1, so part of a reviewer's "scale use" is their role, not their style; role (core vs non-core, per project and time) must be a covariate or the analysis restricted to one role. Votes are also sequential (later reviewers see earlier votes), unlike MultiPref/DICES/PRISM.
**Other candidates:** Bugzilla severity (Mozilla/Eclipse; reporter and triager ids; ordinal trivial…blocker) — check public API/dumps.
**Status:** feasibility only; a protocol amendment (data, filtering, role handling, hypotheses) must precede any result.
